# Мини-воронка: план реализации и защиты

Тестовое: aiogram-бот, YAML-конфиг, дашборд внутри Telegram Mini App.
Приложение работает на локальном компьютере. Сдача: публичный GitHub и видео 1–3 минуты.

## Договорённости о поведении

- /start сохраняет пользователя и показывает приветствие и кнопку отправки телефона.
- Принимаем собственный контакт пользователя в личном чате. Чужой контакт не завершает регистрацию.
- Отсчёт рассылки начинается после первого успешного сохранения телефона.
- Оба интервала считаются от этого момента: +10 секунд и +60 секунд (не +10 и ещё +60).
- Повторные /start и отправка контакта не создают повторную серию сообщений.
- Все тексты воронки и интервалы хранятся в YAML. Секреты — в .env.
- SQLite хранит пользователей и запланированные отправки.
- Дашборд показывает уникальных пользователей, регистрации, конверсию в регистрацию и успешные/ожидающие/неуспешные отправки.
- Успешная отправка означает успешный ответ Bot API; это не подтверждение прочтения сообщения.
- Телефоны на дашборде не показываем.

Это наши явно выбранные трактовки неоднозначностей задания; они войдут в README.

## Архитектура

Один процесс, один экземпляр приложения:

1. FastAPI отдаёт HTML и API агрегированной статистики.
2. aiogram получает обновления через long polling.
3. Фоновая корутина выбирает наступившие отправки из SQLite и обращается к Bot API.
4. Жизненный цикл приложения запускает и завершает фоновые задачи.

SQLite выбран для локального небольшого приложения: не требует отдельного сервера.
Бот и дашборд читают одно хранилище. Очередь отправок сохраняется между запусками.
Будем использовать aiosqlite для доступа из асинхронного приложения.
Несколько процессов и конкурентные воркеры не поддерживаются в первой версии; запуск без reload и с одним worker.

Планируемые модули: config.py, storage.py, bot.py, scheduler.py, web.py, main.py, static/index.html.
Выделяем модуль тогда, когда появляется его ответственность.

## Границы надёжности

- Ограничения UNIQUE защищают от повторного создания пользователя и шагов рассылки.
- Сохранение телефона и создание отправок выполняются одной транзакцией.
- Время отправки сохраняется в UTC; просроченные задания подхватываются после запуска.
- Будут ограниченные повторы для временных ошибок и отдельная обработка недоступного пользователя.
- Нельзя обещать exactly-once отправку: между успешным запросом Telegram и записью результата в SQLite возможен сбой. Поведение этого случая явно описываем в README.
- Синхронный sleep внутри обработчика не используем.

## Mini App и локальный запуск

HTML в обычном браузере — промежуточная проверка. Итоговая демонстрация должна включать открытие внутри Telegram.
Для обычного Telegram-бота потребуется HTTPS-адрес, ведущий на локальный сервер, например временный туннель.
Отдельное окружение Telegram test server допускает HTTP; для него нужны отдельный аккаунт и бот.
Способ демонстрации выбираем и проверяем до финальной полировки.

Для статистики планируем проверять подпись Telegram initData, срок действия и ID администратора из окружения.
Публично доступный HTML не должен предоставлять неавторизованный доступ к API статистики.
Токен бота и номера телефонов не попадают в GitHub, браузерный код и видео.

## Что проверить перед сдачей

1. Новый пользователь: /start, собственный телефон, две отправки примерно через 10 и 60 секунд.
2. Два /start и два одинаковых контакта: одна регистрация и два задания, без повторного запуска серии.
3. Чужой контакт не регистрирует пользователя.
4. Перезапуск до срока отправки: задания и статистика сохраняются.
5. Некорректный YAML: понятная ошибка при запуске.
6. Ошибка отправки видна в статусах; успешные отправки считаются отдельно.
7. API статистики отклоняет запрос без валидной авторизации и от пользователя без прав администратора.
8. Чистый запуск по README воспроизводит приложение; секретов и пользовательской БД в репозитории нет.
